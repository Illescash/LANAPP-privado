Declaración de Variables
Como en otros lenguajes de programación, en kotlin se necesitan variables para almacenar información.
Las declaraciones de variables comienzan por la palabra reservada var seguida del nombre de la variable, dos puntos y el tipo de dato de la variable.
Por ejemplo, el siguiente programa declara que la variable edad es de tipo Int, el tipo adecuado para albergar números enteros en kotlin:
fun main() {
var edad: Int
}
¿Por qué es necesario escribir var?
Quizá te preguntes por qué es necesaria la palabra var en las declaraciones de kotlin:
var edad: Int
¿No sería más sencillo que las declaraciones empezaran por el tipo de dato como en C o Java?
int edad;
Las declaraciones en Kotlin no pueden empezar por el tipo pues éste no siempre se escribe explícitamente. Más concretamente, el tipo de dato es opcional cuando se puede inferir del valor que se asigna a la variable.
Por ejemplo, en la siguiente declaración, Kotlin infiere que edad es de tipo Int a partir del inicializador 25:
var edad = 25
Prueba el siguiente código. ¿Qué tipo asigna? ¿Qué pasa al hacer print?

Tipos no anulables
En lenguajes como Java, una variable de tipo cadena de caracteres (String) puede recibir el valor null, para indicar que todavía no existe.
Es importante distinguir una cadena nula (que vale null) de una cadena vacía como la siguiente, que sí existe:
val nombre = ""
En Kotlin, solo las variables de tipos anulables (nullable types) pueden recibir el valor null.
El tipo String de Kotlin no es un tipo anulable y, por lo tanto, la variable nombre del siguiente programa no puede recibir el valor null:
fun main() {
    var nombre: String
    nombre = null
}

Tipos anulables
Para poder dar a nombre el valor null se puede añadir ? en la declaración

fun main() {
    var nombre: String?
    nombre = null
}
El tipo Nothing?
El tipo Nothing? es un tipo de dato sin valores que Kotlin infiere para las variables que se asignan a null.
En efecto, la siguiente instrucción hace que Kotlin asigne a numero el tipo Nothing?:
var numero = null
Más adelante veremos otra situación en la que se utiliza este curioso tipo de dato.

¿Qué está pasando al añadir ?. al usar nombre.uppercase() en Kotlin?


El operador ?. indica que la variable nombre puede contener el valor null (i.e. que es una variable anulable).

Al usar nombre?.uppercase(), Kotlin comprueba automáticamente si nombre es null antes de llamar al método.

Si nombre es null, la expresión nombre?.uppercase() devuelve null y el programa no lanza una excepción.

El operador ?. fuerza a Kotlin a convertir el valor de nombre en una cadena vacía ("").

Si nombre es null, el programa lanza una excepción

El operador ?. se conoce como safe call operator y se usa para evitar errores por valores nulos.

Kotlin posee dos operadores de comparación:

El operador de comparación referencial, a === b,  que devuelve true si a y b apuntan al mismo objeto*. Para tipos como Int,  Double o String, === es equivalente a ==.
El operador de comparación estructural (a == b), que actúa de la siguiente manera:
a?.equals(b) ?: (b === null)
Es decir, si a no es null, se llama al método equals y, en caso contrario, se ejecuta b === null, que es cierto si b es igual a null como referencia.

Ir al contenido principal
El operador when en Kotlin se utiliza para tomar decisiones según el valor de una expresión, de forma similar al switch de Java, pero es más potente y flexible.

val semaforo = "rojo"

when (semaforo) {
    "rojo" -> println("Detenerse")
    "amarillo" -> println("Precaución")
    "verde" -> println("Avanzar")
    else -> println("Color no válido")
}

Diferencias con Java
Con when no es necesario escribir break en cada caso.
En un switch, olvidar un break puede provocar errores; con when eso se evita.

when puede trabajar no solo con constantes, sino también con objetos y expresiones más complejas, algo que switch en Java no permite.

Uso de when con enumeraciones
Un uso muy común de when es con clases enum, por ejemplo, para asociar valores o descripciones a cada opción posible (como colores, estados, tipos, etc.).

El ejemplo clásico es el de los colores del arcoíris, donde según el color se devuelve una información asociada (por ejemplo, si es un color cálido o frío).
when permite:

Ejecutar solo el bloque que coincide con el valor recibido.

Agrupar varios valores en un mismo caso.

enum class Color {
    RED, ORANGE, YELLOW, GREEN, BLUE, INDIGO, VIOLET
}

fun getWarmth(color: Color) = when(color) {
    Color.RED, Color.ORANGE, Color.YELLOW -> "warm"
    Color.GREEN -> "neutral"
    Color.BLUE, Color.INDIGO, Color.VIOLET -> "cold"
}

fun main(){
    println(getWarmth(Color.ORANGE))
}

Anatomía de una función
El código de una función está compuesto por cabecera y cuerpo:
la cabecera es la primera línea de la función (línea 10),
el cuerpo es el conjunto de instrucciones entre la llave abierta y la cerrada (líneas 11 a 21).
La siguiente figura identifica la cabecera y el cuerpo de la función de este objetivo:

La cabecera
Fíjate en la cabecera de la función califica:
private fun califica(calificacion: Int): String { ... }
Ésta es la información que nos proporciona:
el modificador de visibilidad: private,
la palabra que identifica la declaración de función: fun,
el nombre de la función: califica,
la lista de parámetros de la función: (calificacion: Int),
el tipo de dato devuelto por la función: String.
El modificador private indica que esta función solo se puede utilizar en el fichero Calificaciones.kt donde está definida. El modificador por defecto es public, que es el que se sobreentiende si no escribes un modificador explícitamente.
Los parámetros de una función se comportan como si fueran variables val, es decir, no pueden ser modificados en el cuerpo de la función, sólo consultados.

        return true
    else
        return false

Veamos otro ejemplo:

Supongamos que tenemos la clase Person:

data class Person(val name: String, val age: Int) 
Y queremos encontrar la persona más vieja en una lista. Sin lambdas, podríamos hacerlo manualmente:

fun findTheOldest(people: List<Person>) {
    var maxAge = 0
    var theOldest: Person? = null
    for (person in people) {
        if (person.age > maxAge) {
            maxAge = person.age
            theOldest = person
        }
    }
    println(theOldest)
}

fun main() {
    val people = listOf(Person("Alice", 29), Person("Bob", 31))
    findTheOldest(people)
    // Person(name=Bob, age=31)
}

En Kotlin, hay una forma más concisa usando lambdas y funciones de la librería estándar:

fun main() {
    val people = listOf(Person("Alice", 29), Person("Bob", 31))
    println(people.maxByOrNull { it.age })
    // Person(name=Bob, age=31)
}

maxByOrNull { it.age } busca el elemento con el valor máximo según age.

La lambda { it.age } recibe cada elemento de la colección y devuelve el valor a comparar.

Fíjate en los siguientes detalles del segundo parámetro:
el tipo es una función que acepta un Char y devuelve un Boolean:
(Char) -> Boolean
el parámetro no tiene nombre, a diferencia del primero, cuyo nombre es cadena.
El cuerpo de la función contar utiliza a la función pasada como segundo argumento para contar solo ciertos caracteres, aquellos para los que filtro devuelve true:
    // Función contar definida como variable
    var contar: (String, (Char) -> Boolean) -> Int = { cadena, filtro ->
        var cont: Int = 0
        for (c in cadena)
            if (filtro(c))
                cont++
        cont
    }
Podemos definir una función para pasar a contar como filtro de la siguiente forma:
fun main() {
    // Función filtro
    fun esVocal(c: Char): Boolean {
        return c.lowercaseChar() in "aeiou"
    }

    // Usamos contar pasando la función esVocal
    val texto = "Hola Mundo"
    val numeroVocales = contar(texto, ::esVocal)

    println("Número de vocales en '$texto': $numeroVocales")
}

Las lambdas, y las funciones anónimas, nos permite pasar un trozo de código a otra función sin darle nombre:

La biblioteca estándar de Kotlin está pensada para ser utilizada con lambdas. Por ejemplo, el método count de String se puede llamar sin argumentos para contar el número de caracteres de una cadena:

println("Alameda".count(::filtro))

Una función extendida (extension function en inglés) es una función que se invoca como miembro de una clase pero que se define fuera de la clase.
El código que ves debajo define la extensión ultimo de la clase String. La definición de ultimo es casi igual a la de cualquier otra función salvo por el nombre de la clase extendida, que se coloca en la cabecera seguida de un punto:
fun String.ultimo(): Char {
fun String.ultimo(): Char = this.get(this.length - 1)
}
La cabecera de ultimo indica que es una extensión de la clase String, que no tiene argumentos y que devuelve un Char.
Fíjate en la siguiente llamada al método extendido desde una cadena de caracteres:

En realidad, como la extensión tiene acceso directo a los miembros públicos de la clase (String en este caso), no es necesario utilizar this:
fun String.ultimo(): Char = get(length - 1)
Tipo recibidor
Al definir una función extendida, de alguna manera, estamos añadiendo un nuevo método a la clase o interfaz. Sin embargo, para ello no es necesario tener acceso al código de la clase extendida.
Ni siquiera es necesario que el código de la clase sea Kotlin, puede tratarse de Java, Groovy u otro lenguaje JVM, siempre que esté compilado en una clase.
Al tipo que se extiende se le llama tipo recibidor, y el valor desde el que se llama a la función recibe el nombre de objeto recibidor.
La función extendida es casi como una función de clase salvo por que no tiene acceso a los miembros private o protected de la clase
Propiedades extendidas
Aunque no se pueden añadir campos (fields) extra desde el exterior de una clase, sí se puede acceder a información de la clase como si se tratara de una nueva propiedad de clase.

Las funciones de contexto son una seña de identidad en Kotlin. El objetivo de estas funciones es la ejecución de un bloque de código en el contexto de un determinado objeto. Ese contexto se determina mediante llaves. 
En general, esto va a simplificar el código y a organizarlo, como veremos en esta sección.
Existen 5 funciones de contexto (let, run, with, apply y also) que difieren en los dos siguientes aspectos:
el acceso al objeto dentro del ámbito que crean,
el valor devuelto por la función.
No es sencillo escoger la función adecuada para cada tarea, pues las funciones de contexto comparten muchas características. Intentaremos darte algunas recomendaciones al respecto en las siguientes unidades.

Seguramente conozcáis el patrón de diseño MVC (Modelo Vista Controlador) este patrón permite tener una arquitectura controlada y separada para que el código sea modular, legible, etc.

Ese modelo es ideal cuando la vista simplemente "dibuja" contenido que le manda el controlador tras los requerimientos del usuario, pero hay casos, como es el de Android, en los que la vista tiene información y necesitamos otro tipo de modelo. 

El patrón MVVM es un patrón en el que la Vista tiene relaciones 1 a 1 con otro componente llamado "ViewModel" que trataremos en detalle a lo largo del curso. 

Esto permite cambios reactivos, ya que un cambio en la vista se traduce automáticamente a ViewModel, que es quien tiene conexión con el modelo (Model). La ventaja que ofrece este paradigma es que frente a cambios en el sistema (cambios de una vista a otra, cambios de configuración, rotación de la pantalla, etc) la UI no necesita volver a hacer "peticiones" a un controlador para que recupere y cargue la vista.

¿Qué es el AndroidManifest.xml?

El AndroidManifest es un archivo XML obligatorio que debe estar en la raíz de tu proyecto (en app/src/main/). Funciona como el "certificado de nacimiento" de tu aplicación, donde declaras todo lo que tu app es y necesita antes de que Android la ejecute.

Estructura básica
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools"
    package="com.uam.miapp">

    <!-- Aquí van los permisos -->
    
    <application
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:theme="@style/Theme.MiApp">
        
        <!-- Aquí van los componentes (Activities, Services, etc.) -->
        
    </application>
</manifest>
Elementos principales
1. Etiqueta <manifest>

Es la raíz del documento. Sus atributos más importantes son:

package: Identificador único de tu aplicación (ej: com.uam.saluddigital). Sigue la convención de dominio inverso y debe ser único en Google Play Store.
versionCode: Número entero que representa la versión interna (ej: 1, 2, 3...). Se incrementa con cada actualización.
versionName: Versión legible para usuarios (ej: "1.0", "2.1.5"). Es lo que ven en la tienda.
<manifest 
    package="com.uam.miapp"
    android:versionCode="1"
    android:versionName="1.0">
2. Permisos <uses-permission>

Declaran qué funcionalidades del sistema necesita tu app. Android preguntará al usuario en tiempo de ejecución para permisos sensibles.

<!-- Permisos comunes -->
<uses-permission android:name="android.permission.INTERNET"/>
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE"/>
<uses-permission android:name="android.permission.CAMERA"/>
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE"/>
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE"/>
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"/>
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION"/>
<uses-permission android:name="android.permission.RECORD_AUDIO"/>
Importante: Desde Android 6.0 (API 23), los permisos peligrosos (cámara, ubicación, almacenamiento, etc.) deben solicitarse también en tiempo de ejecución desde el código, no basta con declararlos en el Manifest.

3. Etiqueta <application>

Contiene la configuración global de la aplicación y todos sus componentes.

Atributos comunes:

<application
    android:allowBackup="true"
    android:icon="@mipmap/ic_launcher"
    android:roundIcon="@mipmap/ic_launcher_round"
    android:label="@string/app_name"
    android:theme="@style/Theme.MiApp"
    android:supportsRtl="true"
    android:usesCleartextTraffic="true">
android:icon: Icono de la app que aparece en el launcher
android:label: Nombre visible de la app (mejor usar referencia a string para i18n)
android:theme: Tema visual de la aplicación
android:allowBackup: Permite backup automático de datos
android:usesCleartextTraffic: Permite conexiones HTTP no seguras (por defecto Android solo permite HTTPS)
4. Activities <activity>

Cada pantalla (Activity) de tu app debe declararse aquí.

<activity
    android:name=".MainActivity"
    android:exported="true"
    android:screenOrientation="portrait"
    android:theme="@style/Theme.MiApp.NoActionBar">
    
    <intent-filter>
        <action android:name="android.intent.action.MAIN"/>
        <category android:name="android.intent.category.LAUNCHER"/>
    </intent-filter>
</activity>

<activity
    android:name=".DetalleActivity"
    android:exported="false"
    android:parentActivityName=".MainActivity"/>
Atributos importantes:

android:name: Nombre de la clase Activity (el punto inicial indica el paquete base)
android:exported: true si otras apps pueden lanzarla, false si es solo interna (obligatorio declararlo desde Android 12)
android:screenOrientation: Fija la orientación (portrait, landscape, sensor)
android:parentActivityName: Define la Activity padre para navegación hacia atrás
Intent-filter de LAUNCHER: Indica cuál es la Activity principal que se abre al tocar el icono de la app:

<intent-filter>
    <action android:name="android.intent.action.MAIN"/>
    <category android:name="android.intent.category.LAUNCHER"/>
</intent-filter>
Solo una Activity debe tener este intent-filter (normalmente MainActivity).

5. Services <service>

Para tareas en segundo plano:

<service
    android:name=".services.MiServicio"
    android:enabled="true"
    android:exported="false"/>
6. Broadcast Receivers <receiver>

Para escuchar eventos del sistema:

<receiver
    android:name=".receivers.MiReceiver"
    android:enabled="true"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
    </intent-filter>
</receiver>
7. Content Providers <provider>

Para compartir datos con otras apps:

<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths"/>
</provider>
Ejemplo completo

Buenas prácticas
Usa referencias a recursos: En lugar de texto hardcoded, usa @string/app_name para facilitar traducciones
Minimiza permisos: Solo pide los permisos estrictamente necesarios

¿Qué es Gradle?
Gradle es un sistema de automatización de construcción que gestiona las dependencias y configura la forma en que tu proyecto de Android se compila y ejecuta. Gradle define qué bibliotecas externas usa tu proyecto, cómo se empaqueta la aplicación, cómo se ejecutan las pruebas y mucho más.

Estructura básica de Gradle en un proyecto Android

En un proyecto de Android, hay dos archivos build.gradle principales:

build.gradle (nivel del proyecto): Configura aspectos generales del proyecto y administra los repositorios y las dependencias comunes para todos los módulos de la app.
build.gradle (nivel del módulo/app): Configura la compilación del módulo específico (generalmente la aplicación) y especifica las dependencias específicas para esa aplicación.
1. Archivo build.gradle del nivel del proyecto (root)

Este archivo se encuentra en la raíz de tu proyecto. Aquí es donde defines los repositorios y los complementos (plugins) que se usan en todo el proyecto.

2. Archivo build.gradle del nivel del módulo (app)

Este es el archivo donde defines la configuración específica de tu aplicación, como la versión de compilación, las versiones de las SDK, y las dependencias (bibliotecas) que se usan en el código.

Desglose del archivo build.gradle

1. plugins {}

Esta sección del archivo build.gradle indica los plugins que se usarán en el proyecto. Un plugin es un componente que añade una funcionalidad específica, como la capacidad de compilar aplicaciones Android o utilizar Kotlin.

plugins {

alias(libs.plugins.android.application)

alias(libs.plugins.kotlin.android)

alias(libs.plugins.kotlin.compose)

}

com.android.application: Este plugin le dice a Gradle que este módulo es una aplicación de Android.
org.jetbrains.kotlin.android: Este plugin permite usar Kotlin en la aplicación Android.
2. android {}

El bloque android {} contiene las configuraciones específicas de compilación para el módulo Android. Aquí puedes establecer cosas como la versión de SDK que se utilizará, las versiones de tu aplicación, y configurar opciones avanzadas.

android {

namespace = "com.example.sleep"

compileSdk = 36

defaultConfig {

applicationId = "com.example.sleep"

minSdk = 24

targetSdk = 36

versionCode = 1

versionName = "1.0"

testInstrumentationRunner = "androidx.test.runner.AndroidJUnitRunner"

}

buildTypes {

release {

isMinifyEnabled = false

proguardFiles(

getDefaultProguardFile("proguard-android-optimize.txt"),

"proguard-rules.pro"

)

}

}

compileOptions {

sourceCompatibility = JavaVersion.VERSION_11

targetCompatibility = JavaVersion.VERSION_11

}

kotlinOptions {

jvmTarget = "11"

}

buildFeatures {

compose = true

}

}

Desglose:

namespace: Define el espacio de nombres único para tu aplicación, generalmente basado en el paquete de tu proyecto.
compileSdk: Especifica la versión del SDK de Android con la que se compilará la aplicación.
minSdk: Define el SDK mínimo que los dispositivos deben tener para ejecutar la app. Aquí es API 24 (Android 7.0).
targetSdk: Define la versión del SDK para la cual la app está optimizada.
buildFeatures.compose = true: Habilita el soporte para Jetpack Compose en el proyecto.
composeOptions.kotlinCompilerExtensionVersion: Especifica la versión del compilador que se usará para compilar el código de Jetpack Compose.
kotlinOptions.jvmTarget: Especifica la versión de la JVM (Java Virtual Machine) para Kotlin, aquí se usa la 11.
3. dependencies {}

El bloque dependencies {} es donde defines las bibliotecas externas o dependencias que tu proyecto necesita para funcionar. Estas bibliotecas pueden ser descargadas desde repositorios como google() o mavenCentral().

Modifica el archivo 'build.gradle (Module: app)' para añadir las dependencias necesarias:

Los niveles API 
Al crear el proyecto especificamos el nivel API más bajo en el que se puede ejecutar la app (desde el punto de vista del usuario sería la versión del sistema). Además de este nivel, la app cuenta con un nivel API con el que se compila, y un nivel API objetivo, o target.

El nivel API especificado en minSdk especifica la versión de Android más antigua en la que se puede ejecutar la app. 
Gradle compila la app con el nivel API compileSdk. Es la versión más reciente de Android que acepta la app, es decir, la app puede utilizar las APIs de este nivel o inferiores, pero no de niveles superiores.
El nivel API especificado en targetSdk es el API más reciente con el que se ha probado la app, que suele coincidir con el nivel de compilación.

Elementos vacíos
Un elemento vacío no contiene ningún otro elemento en su interior. Todos los elementos del fichero que hemos creado son vacíos salvo RelativeLayout. 
Elementos compuestos
Un elemento compuesto, puede contener en su interior a otros elementos, ya sean simples o compuestos.

Un elemento compuesto no se puede cerrar como los elementos vacíos. Es necesario utilizar una etiqueta de cierre después de haber cerrado todos los demás elementos que contiene.

</RelativeLayout>

La clase R
La clase R es una clase Java autogenerada donde se almacenan los identificadores de los recursos. Este fichero no debes modificarlo. 

Los recursos están organizados en subclases estáticas de R como, por ejemplo, color, dimen, drawable o layout. Estos identificadores se pueden utilizar dentro del código para acceder a los recursos correspondientes.

/* AUTO-GENERATED FILE. DO NOT MODIFY.
 *
 * This class was automatically generated by the
 * aapt tool from the resource data it found. It
 * should not be modified by hand.
 */

package com.example.curso_android;

public final class R {
    public static final class anim { ... }
    public static final class attr { ... }
    public static final class bool { ... }
    public static final class color {
       public static final int colorPrimary=0x7f040027;
       ...
    }
    public static final class dimen { ... }
    public static final class drawable { ... }
    public static final class id { ... }
    public static final class layout { ... }
    public static final class mipmap { ... }
    public static final class string { ... }
    public static final class style { ... }
    ...
}

Cada vez que llamamos al método findViewById para capturar una referencia a una vista, Android debe navegar por la jerarquía de vistas de la aplicación. Este trabajo lleva tiempo, especialmente en aplicaciones con un gran número de vistas que gestionar.

Jetpack alivia este problema mediante la biblioteca de vinculación de datos (data binding). Esta biblioteca permite guardar las referencias a las vistas en un objeto que se carga al comienzo de la aplicación, y cuyas referencias pueden ser consultadas después sin necesidad de volver a navegar por la jerarquía de vistas.

Además, la vinculación de datos nos va a permitir conectar las vistas de la app (el TextView de la pregunta) con los datos (el texto de la pregunta) de forma declarativa (en el fichero XML), en lugar de mediante código.

Es necesario habilitar la vinculación de datos para poder utilizar esta herramienta en nuestro proyecto.

Debes abrir el fichero build.gradle.kts (Module: app) y añadir una sección buildFeatures dentro de la sección android:

android {
    namespace = "com.example.playground"
    compileSdk {
        version = release(36)
    }

    defaultConfig {
        applicationId = "com.example.playground"
        minSdk = 24
        targetSdk = 36
        ...
    }
    buildFeatures {
        dataBinding = true
    }
}

Hay dos maneras de manejar eventos como los clics de los botones con la vinculación de datos:

Referencia a métodos: la expresión contiene una referencia a un método que encaja en la signatura del método callback como, por ejemplo, onClick. La implementación se crea durante la vinculación.
Vinculación de escuchadores: expresiones lambda que se evalúan cuando ocurre el evento. Solo es necesario que el valor devuelto encaje en la signatura, no los parámetros. La implementación se crea cuando ocurre el evento, no durante la vinculación. 
Referencia a método
El nombre de referencia a método proviene del hecho de que la expresión de vinculación contiene una referencia al método que se desea ejecutar:

@{sorpresa::update_from_view}
En general, el nombre del atributo que hay que utilizar viene determinado por el nombre del método callback. Por ejemplo, android:onClick para el método onClick de la interfaz View.OnClickListener:

<Button    
    ...
    android:onClick="@{sorpresa::update_from_view}"
    ...
La signatura del método referenciado debe coincidir con la del método callback correspondiente, onClick en este caso una nueva función en Sorpresa.kt que tiene el siguiente aspecto

fun update_from_view(view: View) {
     level = when(view.id) {
         R.id.first_button -> 5
         R.id.reset_button -> 10
         R.id.third_button -> 0
         else -> throw Exception("Unavailable level")
     }
}
Vinculación de escuchadores
La otra forma de gestionar eventos utiliza una lambda en la expresión de vinculación:

<Button
    ...
    android:onClick="@{()->sorpresa.update_level(10)}
    ...
No olvides los paréntesis de la llamada, pues esto no es una referencia a función sino una llamada:

Las intenciones nos van a permitir lanzar una actividad desde otra. 

Si recuerdas las primeras secciones, tuvimos que indicar en el Manifest, qué actividad había que lanzar primero. 

Hasta el momento, no hemos tenido que instanciar ni arrancar la actividad MainActivity, sino que Android se ha encargado de hacerlo por nosotros. 

En general, los proyectos suelen contener más de una actividad. Es frecuente, además, tener que arrancar una actividad desde otra, para lo que vamos a necesitar intenciones, objetos de la clase Intent.

El nombre no es casual, pues en realidad lo que vamos a hacer es declarar la intención de llevar a cabo una tarea, para que Android termine de escoger la mejor manera de llevarla a cabo.

La clase Intent
Para arrancar una actividad desde otra vamos a utilizar el método startActivity , que necesita un objeto de tipo Intent como argumento:

startActivity(intent)
El objeto de tipo Intent permite que la actividad comunique al gestor de actividades (ActivityManager) que desea que se arranque otra actividad.

El constructor de la clase Intent necesita dos argumentos: un contexto (this), y la actividad que se desea arrancar (MainActivity):

val intent: Intent = Intent(this, MainActivity::class.java)
Si la nueva actividad no está declarada en el fichero de manifiesto, el gestor de actividades se encargará de lanzar una excepción ActivityNotFoundException.

Intenciones implícitas
La intención que se define indicando una actividad es una intención explícita, pues se indica explícitamente qué actividad se desea arrancar (MainActivity):

startActivity(Intent(this, MainActivity::class.java))
También podemos escribir intenciones implícitas, en las que no indicamos la actividad sino la acción que deseamos ejecutar. Por ejemplo, para enviar un mensaje, la acción ACTION_SHARE se pasa como argumento del constructor del objeto Intent. 

En este caso, Android se encarga de buscar una actividad que pueda llevar a cabo la tarea:

val intent = Intent(Intent.ACTION_SEND)
intent.setType("text/plain")
intent.putExtra("MESSAGE", "Saludos")
startActivity(intent)
Los filtros de intenciones
Con el objetivo de encontrar una actividad adecuada para una acción, Android utiliza los filtros que declaran las actividades en el fichero de manifiesto. 

Concretamente, comprueba los elementos intent-filter dentro del elemento activity, como el de nuestra actividad TitleActivity:

<activity android:name=".TitleActivity">
<intent-filter>
<action android:name="android.intent.action.MAIN" />
<category android:name="android.intent.category.LAUNCHER" />
</intent-filter>
</activity>
Como ves, hay dos elementos diferenciados, action y category:

la acción es MAIN , lo cual indica que ésta es la actividad que se lanza al arrancar la aplicación,
la categoría es LAUNCHER, lo cual hace que el icono de la actividad se muestre en el launcher o pantalla de inicio. Con frecuencia verás otra categoría, DEFAULT, que es la adecuada para que la actividad pueda ser arrancada por otras.

Una actividad puede estar en uno de los siguientes estados a lo largo de su vida:

inexistente: no se ha arrancado todavía o acaba de ser destruida,

detenida (stopped): está oculta completamente por otra actividad lanzada después,

en pausa (paused): está parcialmente oculta por otra actividad medio transparente o una ventana de diálogo,

reanudada (resumed): está visible del todo y el usuario puede interactuar con ella.

En las transiciones entre estos estados se ejecutan los llamados métodos del ciclo de vida, de los que ya conoces uno: el método onCreate. 
Como en el caso de onCreate, estos métodos no se llaman explícitamente. Es Android quien se encargar de ejecutarlos en su debido momento. La tarea del programador consiste en sobrescribirlos para modificar el comportamiento de la actividad.

El estado reanudada es un estado estable del que solo puede disfrutar una actividad en cada momento. Compáralo por ejemplo, con el estado detenida, en el que puede haber numerosas actividades.

Si bien es un estado estable, una actividad puede abandonarlo de varias maneras como, por ejemplo, pulsando el botón Back. Al pulsar el botón Back, la actividad recorre los estados que hemos descrito en sentido inverso, lo que involucra nuevos métodos del ciclo de vida, que podríamos considerar opuestos a los estudiados hasta ahora.

La biblioteca Lifecycle da la vuelta al ciclo de vida, pues permite que otras clases observen y reaccionen al ciclo de vida de MainActivity. De esta forma, el reproductor va a poder disparar la ejecución de sus métodos sin tener que sobrescribir los métodos de la actividad.

Las tres componentes principales de la biblioteca Lifecycle son:

Lifecycle owners (propietarios de ciclo de vida) como MainActivity y, en general, cualquier componente que posea un ciclo de vida.
La clase Lifecycle que contiene el estado de un propietario de ciclo de vida, y puede disparar eventos cuando el estado cambia.
Lifecycle observers (observadores de ciclos de vida), que implementan la interfaz DefaultLifecycleObserver, y observan el ciclo de vida de propietarios, ejecutando acciones cuando se observan cambios.
Imagina una clase Player que inicie y detenga un reproductor. Este tendría que iniciarse al inicio de la aplicación y parar cuando esta se detenga, sin LifeCycle deberíamos de hacer algo así:

declarar una propiedad de tipo Player en MainActivity e instánciala; llamar al método start en el método onStart de MainActivity, llamar al método stop en el método onStop de MainActivity.

Podemos evitar esto haciendo que la clase Reproductor implemente la interfaz LifecycleObserver

class Player() : DefaultLifecycleObserver{...}

Android proporciona una clase que sobrevive a los cambios de configuración del dispositivo (giros, por ejemplo), y solo se destruye cuando se finaliza la actividad a la que está asociado: la clase ViewModel de la biblioteca Jetpack.

import com.example.playground.model.Sorpresa
import timber.log.Timber

class MainViewModel : ViewModel() {
    var sorpresa = Sorpresa("Pulsa el botón", "NUEVA SORPRESA")

    init {
        Timber.i("MainViewModel created")
    }

    override fun onCleared() {
        super.onCleared()
        Timber.i("MainViewModel destroyed")
    }

Para que funcione el viewModel debemos asociar la actividad con una instancia de esta clase.

Para asociar la actividad con una instancia de MainViewModel necesitamos al proveedor de modelos: ViewModelProvider. Esta clase devuelve un ViewModel ya existente si es que existe uno, o crea uno nuevo cuando no existe ninguno. Instanciando ViewModelProvider en MainActivity estaremos asociandolas.

Es importante que la actividad contenga una referencia a ViewModel y no al revés. El ViewModel no debe contener referencias ni a la actividad ni a las vistas, pues no sobreviven a la rotación.

El objeto de tipo ViewModel permanece en memoria frente a cambios de configuración del dispositivo como rotaciones, por ejemplo.

Cada vez que se rota el dispositivo y se ejecuta onCreate, ViewModelProvider devuelve la misma instancia del objeto de tipo MainViewModel, no una nueva. El objeto permanece en memoria, y solo se destruye cuando se destruye la actividad, al pulsar el botón Back, por ejemplo.
Al rotar, la actividad se destruye y luego se recrea pero el objeto de tipo ViewModel sobrevive. Solo se destruye cuando la actividad finaliza, por ejemplo al pulsar el botón Back:

Una de las formas que tenemos que asociar la actividad principal a ViewModel es instanciándola desde MainActivity
Como ves a continuación, ViewModelProvider tiene como argumento un contexto, que especifica el ámbito para el que se solicita el ViewModel, en este caso this, es decir, la actividad MainActivity:
    private val viewModel: MainViewModel by lazy {
        ViewModelProvider(this).get(MainViewModel::class.java)
    }
Como el objeto de tipo MainViewModel solo se crea una vez durante el ciclo de vida de la actividad, podemos utilizar una referencia val para guardarlo. Sin embargo, no se puede inicializar en la declaración, se debe esperar a que la actividad se haya creado. Además, no podemos utilizar el modificador lateinit porque solo se puede aplicar a variables var.  Es por eso que utilizamos inicialización lazy, que se ejecuta la primera vez que se invoca el objeto. Siempre se recuperará el mismo objeto, incluso aunque la actividad se recree.

LiveData es una clase pensada para contener datos de tipo arbitrario cuyos cambios pueden ser observados desde las actividades del proyecto. Los cambios de los datos son notificados automáticamente a la actividad observadora, que puede así responder adecuadamente.

Además, los objetos de tipo LiveData son conscientes del ciclo de vida de la actividad que los observa. Esta consciencia del estado de la actividad es una propiedad muy interesante, pues simplifica la forma en que la actividad se actualiza u observa los datos.

En lugar de complicar el código haciendo comprobaciones costosas, como se hacía antes de disponer de la clase LiveData, la actividad solo será notificada de actualizaciones de los datos cuando se encuentre en un estado activo.

La clase LiveData es abstracta y, por lo tanto, no se puede utilizar directamente, es necesario extenderla. Sin embargo, la clase MutableLiveData se puede instanciar directamente.

La clase MutableLiveData es genérica y necesita que se especifique el tipo de dato envuelto por la clase. Concretamente, la siguiente declaración declara el objeto liveData que contiene un valor entero en su interior:

var liveData = MutableLiveData<Int>()
Si en lugar de un entero, necesitaras envolver una cadena de caracteres, deberías hacer lo siguiente:

var liveData = MutableLiveData<String>()
Los objetos de tipo LiveData cuentan con una propiedad, value, donde se aloja el valor envuelto por el objeto. Así, la siguiente instrucción asigna el valor 5 a la propiedad value del objeto liveData:

liveData.value = 5
MutableLiveData<Int> nos permite almacenar un entero que se dice vivo porque va a ser consciente del estado de la actividad que lo observe. Así, la actividad solo será notificada de cambios del dato cuando pueda gestionarlos, no si está detenida, por ejemplo.

En general, los objetos LiveData se van a declarar dentro del ViewModel para evitar su destrucción después de las rotaciones.

La biblioteca Jetpack posee una interfaz, Observer, para observar notificaciones de datos vivos.

La actividad va a observar el objeto de tipo LiveData mediante una implementación de la interfaz Observer, con su método onChanged. El código colocado dentro de onChanged es el que se ejecutará cada vez que se modifique el dato.

Para usar esta biblioteca debemos instanciar un observador en la actividad principal para implmentar la interfaz en el método OnCreate. Recuerda que una expresión objeto define e instancia simultáneamente una clase que, en este caso, implementa la interfaz Observer<Int>

El objeto debe sobrescribir el método callback de la interfaz, onChanged, que se ejecutará cada vez que se modifique el valor del objeto observado (t).

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val observer = object: Observer<Int> {
        override fun onChanged(t: Int?) {
            binding.infoTextView?.text = t.toString()
        }
    }
    // Conecta observer con atributos a observar
Para observar necesitamos usar el método observe, que tiene dos argumentos:

el primero es la actividad que observa las notificaciones (this),
el segundo es el observador que hemos definido en la actividad (observer).
Una de las grandes ventajas de las expresiones objeto es que nos permiten implementar una interfaz sin dar nombre ni a la clase ni a la instancia.

Así que, en la práctica, podemos prescindir de la variable observer y pasar directamente el objeto como argumento del método observe:
override fun onCreate(savedInstanceState: Bundle?) {
    ...
    viewModel.nDueSurprises.observe(this, object: Observer<Int> {
        override fun onChanged(t: Int?) {
            binding.infoTextView.text = t.toString()

Algo imprescindible en aplicaciones Android es la flexibilidad en la interfaz de usuario, ya que debe de lanzarse en escenarios diversos, tamaños de pantalla, modos verticales y apaisados, con o sin menús de navegación, barras de información... Esa flexibilidad podemos entenderla como la capacidad de formar y volver a formar la vista de la actividad en tiempo de ejecución para cualquier requisito del usuario. 
Las actividades no se diseñaron con este tipo de flexibilidad en mente. 

Las actividades están pensadas para controlar una ventana completa de la aplicación, así que una sola actividad debe ser capaz de renderizar todo en la aplicación para que se muestre en pantalla a tiempo. Las actividades, como hemos visto están fuertemente atadas a pantalla que esté en uso. Se podría hacer todo con actividades, pero de cara a la escalabilidad complicaría mucho la situación, haciendo la aplicación compleja y menos mantenible. 

Los fragmentos fueron introducidos en el API 11 debido a la aparición de las tabletas, y la consiguiente necesidad de flexibilizar las interfaces de las aplicaciones.

Los fragmentos tienen muchas características en común con las actividades pues se definen en una clase Kotlin, su interfaz se especifica en un fichero de diseño, y poseen ciclo de vida.

A diferencia de las actividades, varios fragmentos pueden estar activos en la pantalla simultáneamente y, además, un mismo fragmento puede ser compartido por varias actividades, lo que evita repetir código innecesariamente.

Como ocurre con las actividades, la interfaz de los fragmentos se especifica en ficheros de diseño, cuya notación sigue las mismas reglas que los ficheros de diseño de las actividades. Así, el nombre del fichero de diseño del fragmento TitleFragment es fragment_title.xml, igual que activity_title.xml es el fichero de diseño de  TitleActivity.

Los fragmentos que debes utilizar son los de la biblioteca Jetpack. Es importante que recuerdes que no debes utilizar ni los fragmentos originales, ni los de la biblioteca de v4 apoyo, pues no recibirán actualizaciones a partir de Android 9.0 (API 28). El gestor de fragmentos
Para intercambiar fragmentos en ese contenedor de fragmentos tenemos el gestor de fragmentos de la actividad, supportFragmentManager, nos va a permitir añadir el fragmento dentro del contenedor de la actividad. A pesar de su prefijo support, que sugiere su pertenencia a la biblioteca de apoyo, forma parte ya de la biblioteca Jetpack.
class TitleActivity : AppCompatActivity() {
    lateinit var binding: ActivityTitleBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        binding = DataBindingUtil.setContentView(this, R.layout.activity_title)

        val fragment = TitleFragment()

        supportFragmentManager
            .beginTransaction()
            .add(R.id.fragment_container, fragment)
            .commit()
    }
}
Después de instanciar el fragmento, la llamada a beginTransaction devuelve una transacción que permite agrupar operaciones de adición, remplazado o eliminación de fragmentos. En este caso solo necesitamos el método add para añadir un fragmento:

el primer argumento es el identificador del fragmento,
el segundo argumento es el objeto de tipo fragmento.
Los métodos como add (replace, remove) devuelven una instancia de FragmentTransaction, lo cual permite encadenar las llamadas cómodamente. Una vez efectuadas todas las operaciones (en este caso una única llamada a add), todas ellas se ejecutan de forma segura con la llamada final al método commit.

Aunque parezca extraño, el gestor de fragmentos identifica los fragmentos mediante el id del contenedor donde se muestran. Es por eso que en el método add se incluye el id del fragmento.

La lista de fragmentos 
El gestor de fragmentos mantiene una lista de fragmentos en su interior, cada uno de ellos identificado de forma única por el id del contenedor en el que está incrustado, es decir, fragment_container en nuestro caso.

Prueba a rotar el dispositivo cuando el fragmento StudyFragment está visible. Verás que se vuelve a crear y visualizar el fragmento TitleFragment. Esto se soluciona evitando la transacción después de las rotaciones. 

Cuando el dispositivo gira, el gestor de fragmentos hace uso de la lista para recrear los fragmentos automáticamente. En casos como éste, no es necesario instanciar y añadir explícitamente el fragmento.

Para comprobar si un fragmento está en la lista, se llama al método findFragmentById. Ahora la operación se ejecuta sólo cuando el fragmento no está en la lista, es decir, cuando el método devuelve null.

Modifica TitleActivity para ejecutar la transacción sólo si el fragmento no está ya en la lista de fragmentos del gestor.

Utiliza el depurador para probar lo que acabamos de explicar. Coloca un punto de corte y comprueba que, al girar el dispositivo, no se entra en el cuerpo de la instrucción if. El gestor de fragmentos recrea el fragmento adecuado automáticamente.

La pila de fragmentos 
Una transacción se puede añadir a la pila backstack con una llamada al método addToBackStack, como en el siguiente ejemplo:

supportFragmentManager
    .beginTransaction()
    .add(R.id.fragment_container, fragment)
    .addToBackStack(null)
    .commit()
Gracias a este procedimiento, la transacción se puede deshacer pulsando el botón Back del dispositivo sobre el fragmento.

La actividad volverá al estado anterior a la transacción, como vamos a comprobar a continuación.

Resumiendo...
El supportFragmentManager es el componente central en la gestión de fragmentos dentro de una actividad: permite añadir, reemplazar y eliminar fragmentos mediante transacciones atómicas que se confirman con commit().

Internamente, mantiene una lista de fragmentos identificados por el id de su contenedor, lo que le permite recrearlos automáticamente tras eventos como la rotación del dispositivo, evitando así instanciaciones redundantes mediante findFragmentById().

Además, cada transacción puede incorporarse a la pila de retroceso con addToBackStack(), lo que permite al usuario deshacer navegaciones pulsando el botón Back y devolver la actividad al estado anterior, dotando así al flujo de pantallas de un comportamiento coherente e intuitivo.

Al arrancar la transacción que crea SurpriseFragment desde TitleFragment estamos perdiendo la modularidad del fragmento. Además, estamos dando por hecho que TitleActivity puede alojar al fragmento SurpriseFragment.

El fragmento TitleFragment precisa de otro fragmento para su correcto funcionamiento.

Lo que buscamos en esta unidad es evitar esta situación manteniendo la funcionalidad. Para ello delegaremos en la actividad TitleActivity la tarea de crear el fragmento SurpriseFragment.

En lugar de ejecutar esta operación directamente, el fragmento TitleFragment va a declararla en una interfaz de interacción:

class TitleFragment : Fragment() {

    interface OnTitleFragmentInteractionListener {
        fun onSurprise()
    }
    var listener: OnTitleFragmentInteractionListener? = null

    ...
}
En general, los métodos de estas interfaces, como onSurprise, corresponden a operaciones que se escapan a la responsabilidad del fragmento, y deben ser implementadas por la actividad contenedora.

A través de la propiedad listener, el fragmento va a solicitar la ejecución de la transacción a la actividad, en lugar de hacerlo directamente.

Gracias a la interfaz de interacción, toda actividad que quiera utilizar el fragmento TitleFragment, se ve obligada a implementar el método onSurprise. La modularidad del fragmento TitleFragment se salvaguarda a la vez que mantenemos la funcionalidad de la app.

Necesitamos que listener apunte a la actividad que implementa la interfaz, aunque eso podamos hacerlo con la declaración que hemos visto antes. La duda es... ¿cuando?

Si lo asignamos antes de que el fragmento esté ligado a la Activity, no sabemos qué Activity es.
Si lo hacemos después de onCreateView, puede ser demasiado tarde en el ciclo de vida, o podría ser null si el fragmento se reutiliza en otra Activity.
El método onAttach del ciclo de vida del fragmento se ejecuta cuando el fragmento se liga a la actividad. De hecho, el argumento de tipo Context es la actividad alojadora, que se asigna a la propiedad listener:

override fun onAttach(context: Context) {
    super.onAttach(context)
    listener = context as OnTitleFragmentInteractionListener?
}
Además, nos aseguramos de que la actividad implementa la interfaz de interacción del fragmento.  Si no es el caso, la siguiente conversión de tipos dará lugar a una excepción y el programa se detendrá:

context as OnTitleFragmentInteractionListener?
En el método onDettach del fragmento, a partir del cual ya no podemos contar con la actividad anfitriona, pondremos el escuchador a null:

override fun onDetach() {
    super.onDetach()
    listener = null
}
Si se sobrescriben los métodos onAttach y onDetach, la aplicación genera una excepción de conversión de tipos porque TitleActivity no implementa la interfaz de interacción de TitleFragment. Podríamos solucionarlo haciendo que TitleActivity implemente la interfaz OnTitleFragmentInteractionListener del fragmento y sobrescribiendo sus métodos, de manera que el fragmento tenga un listener válido y la conversión de tipos en onAttach() funcione correctamente.

    lateinit var binding: ActivityTitleBinding

    // Sobrescribe el método onSurprise
    override fun onSurprise() {

        val surpriseFragment = SurpriseFragment()

        // Ejecuta la transacción para reemplazar TitleFragment por SurpriseFragment
        supportFragmentManager.beginTransaction()
            .replace(R.id.fragment_container, surpriseFragment)
            .addToBackStack(null) // permite volver atrás con el botón Back
            .commit()
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        binding = DataBindingUtil.setContentView(this, R.layout.activity_title)

        var fragment = supportFragmentManager
            .findFragmentById(R.id.fragment_container)

        if (fragment == null){
            fragment = TitleFragment()

            supportFragmentManager
                .beginTransaction()
                .add(R.id.fragment_container, fragment)
                .addToBackStack(null)
                .commit()
        }
    }
}

class TitleFragment: Fragment() {
    interface OnTitleFragmentInteractionListener {
        fun onSurprise()
    }
    var listener: OnTitleFragmentInteractionListener? = null

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View? {
        val binding = DataBindingUtil.inflate<FragmentTitleBinding>(
            inflater,
            R.layout.fragment_title,
            container,
            false
        )

        binding.titleTextView.setOnClickListener {
            // Llama al método onSurprise de la Activity que implementa la interfaz
            listener?.onSurprise()
        }

        return binding.root
    }

    override fun onAttach(context: Context) {
        super.onAttach(context)
        listener = context as OnTitleFragmentInteractionListener?
    }

    override fun onDetach() {
        super.onDetach()
        listener = null
    }
}
Debido a la interfaz de interacción y a la conversión de tipos dentro del método onAttach, cualquier actividad que aloje un TitleFragment debe implementar el método onSurprise.

En concreto, hemos colocado en onSurprise el código que substituye el fragmento TitleFragment por el fragmento SurpriseFragment. Ahora los fragmentos se comunican a través de la actividad, manteniendo así su modularidad.

Por ejemplo, podríamos crear en onSurprise un fragmento diferente a SurpriseFragment para abrir otra tanda de sorpresas. Es decir, TitleFragment y SurpriseFragment dejan de estar vinculados como lo estaban al principio de esta unidad.

En Android, los fragmentos pueden recibir información mediante argumentos, de manera similar a los Bundle en actividades.

Para hacerlo de forma segura usamos Navigation Safe Args, que genera clases y métodos que garantizan el tipo correcto al pasar y recibir datos.

Configuración de Safe Args
Añadir la dependencia en build.gradle (Project):

buildscript {
    dependencies {
        classpath("androidx.navigation:navigation-safe-args-gradle-plugin:2.7.2")
    }
}
Añadir el plugin en build.gradle (Module: app):

plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
    id("androidx.navigation.safeargs.kotlin")
}
Al reconstruir el proyecto, se generan automáticamente clases NavDirections para cada fragmento.

Pasar argumentos a un fragmento
Supongamos que tenemos un fragmento SurpriseEditFragment que necesita el id de la sorpresa a editar, que se activará por ejemplo al pulsar en el texto de la sorpresa mostrado en SurpriseFragment.

Edita navigation.xml en modo Design.

Selecciona SurpriseEditFragment y añade un argumento:

Nombre: surpriseId

Tipo: String

Para navegar al fragmento pasando el argumento:

val surpriseId = viewModel.currentSurprise.value?.id ?: return@setOnClickListener
val action = SurpriseFragmentDirections
    .actionSurpriseFragmentToSurpriseEditFragment(surpriseId)
findNavController().navigate(action)
surpriseId es el identificador de la sorpresa que queremos editar.

Acceder a los argumentos en el fragmento
Dentro de SurpriseEditFragment:

val args = SurpriseEditFragmentArgs.fromBundle(requireArguments())
val surpriseId = args.surpriseId
val surprise = SurprisesApplication.getSurprise(surpriseId)
binding.surprise = surprise
fromBundle extrae los argumentos de manera segura.

surpriseId se usa para recuperar la sorpresa desde la aplicación o base de datos.

Control del botón Back
Por defecto, Android vuelve al fragmento anterior al pulsar Back.
Si queremos evitar regresar a la edición anterior, usamos popUpTo y popUpToInclusive en las acciones de navegación:

<action
    android:id="@+id/action_surpriseEditFragment_to_surpriseFragment"
    app:destination="@id/surpriseFragment"
    app:popUpTo="@id/surpriseFragment"
    app:popUpToInclusive="true" />
popUpTo vacía la pila hasta el destino.

popUpToInclusive="true" elimina también el destino especificado.

Esto asegura que al volver desde SurpriseEditFragment no se regrese a SurpriseFragment en estado anterior.

class SurpriseEditFragment : Fragment() {

    private var _binding: FragmentSurpriseEditBinding? = null
    private val binding get() = _binding!!

    // Recibimos los argumentos generados por Safe Args
    private val args: SurpriseEditFragmentArgs by navArgs()

    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = FragmentSurpriseEditBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        // Recuperamos la sorpresa usando el ID pasado como argumento
        val surpriseId = args.surpriseId
        val surprise = SurprisesApplication.getSurprise(surpriseId)
        binding.surprise = surprise

        // Configuramos TextWatcher para actualizar la pregunta en tiempo real
        val questionTextWatcher = object : TextWatcher {
            override fun beforeTextChanged(s: CharSequence?, start: Int, count: Int, after: Int) {}
            override fun onTextChanged(s: CharSequence?, start: Int, before: Int, count: Int) {
                binding.surprise?.question = s.toString()
            }
            override fun afterTextChanged(s: Editable?) {}
        }
        binding.questionEditText.addTextChangedListener(questionTextWatcher)
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null
    }
}
